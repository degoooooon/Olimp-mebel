# Мебельный склад «Олимп»

Сайт мебельного склада в селе Александровском Ставропольского края: каталог
на 41 товар с фильтрами, поиском и корзиной. Работает: **[olimp-mebel26.ru](https://olimp-mebel26.ru)**

Без фреймворка. Вся страница в сжатом виде весит 25 КБ — 19,7 КБ скриптов
и 5,8 КБ стилей.

## Если открыл репозиторий впервые

Читать подряд не надо. Пять файлов по порядку — и понятно, как работает
весь каталог:

| Куда | Что там | Зачем это первым |
|---|---|---|
| [docs/catalog-data.md](docs/catalog-data.md) | Формат каталога | Договор между темой и браузером. Всё остальное — про то, как его выполняют |
| [src/js/data.js](src/js/data.js) | Откуда берутся товары | Единственное место, где данные попадают в скрипт. Там же `@typedef` с полями товара |
| [src/js/catalog.js](src/js/catalog.js) | Фильтры и отрисовка | Главная логика витрины: один `filter` с четырьмя условиями |
| [build/wp-template.js](build/wp-template.js) | Как из вёрстки получается тема | Самое неочевидное место проекта, см. предупреждение ниже |
| [wp-theme/olimp/functions.php](wp-theme/olimp/functions.php) | Сторона WordPress | Тип записи, таксономия и печать каталога |

Отдельно стоит прочесть [docs/journal.md](docs/journal.md), если интересно
не «как сделано», а «почему именно так»: там разобраны поломки, из которых
выросло большинство решений в коде.

Если удобнее смотреть в браузере, есть
**[справочник по модулям](https://degoooooon.github.io/Olimp-mebel/docs/)** —
все функции с параметрами и типами. Он собран из комментариев JSDoc прямо
в коде командой `npm run docs` и пересобирается в CI на каждый пуш, поэтому
отстать от кода не может. Отвечает на вопрос «что делает эта функция»;
на вопрос «как всё устроено» отвечает схема ниже.

## Как данные доходят до карточки

```
        Админка WordPress
                │   владелец заводит товар: название, цена, фото, характеристики
                ▼
        functions.php · olimp_products()
                │   собирает массив товаров из своего типа записи
                │
                ├──▶ olimp_cards()          карточки готовой разметкой
                │                           видит поисковик и человек без JS
                │
                └──▶ olimp_catalog_json()   те же товары блоком JSON
                    │                       <script id="catalog-data">
                    ▼
                    src/js/data.js          читает блок и проверяет формат
                    │                       блока нет — демо-набор для статики
                    ▼
                    src/js/catalog.js       фильтрует, сортирует, рисует сетку
                    │
                    ├──▶ url-state.js       состояние уходит в адрес страницы
                    └──▶ cart.js            корзина живёт в localStorage
```

Товары печатаются **дважды намеренно**: разметкой — чтобы страница была
полной ещё до запуска скрипта, и JSON — чтобы фильтры работали без
перезагрузки. Оба раза из одного массива, поэтому разойтись они не могут.

Страница товара устроена иначе: её собирает PHP целиком
(`single-olimp_product.php`), а браузеру остаётся галерея и счётчик корзины.

## Две сборки из одних исходников

Главная особенность проекта. Одни и те же `src/index.html`, `src/styles/`
и `src/js/` собираются в два разных результата:

```bash
npm run build         # статический сайт в dist/ — для просмотра без WordPress
npm run build:theme   # тема WordPress в wp-theme/olimp/ — то, что стоит на хостинге
```

Разметка при этом остаётся в одном месте. Плагин `build/wp-template.js`
превращает `index.html` в `front-page.php`: подменяет адреса на вызовы
WordPress, вставляет `wp_head()` и точки, куда PHP печатает каталог.

Так исправление в вёрстке попадает и в статику, и в тему одной командой,
а не переносится руками в два файла с риском разойтись.

## Команды

```bash
npm install           # один раз

npm start             # dev-сервер, сам откроет localhost:3000
npm run dev:phone     # то же, но доступно с телефона в той же сети
npm run build         # статика в dist/
npm run build:theme   # тема WordPress
npm run preview       # локальный просмотр собранного dist/
npm run lint          # eslint + типы + stylelint + linthtml + editorconfig
npm run docs          # справочник по модулям из JSDoc в docs-site/
```

## Как устроен каталог

Товары и категории ведёт владелец сайта в админке WordPress — свой тип
записей и своя таксономия, никаких плагинов. Путь данных нарисован
[выше](#как-данные-доходят-до-карточки).

Формат блока JSON описан в [docs/catalog-data.md](docs/catalog-data.md),
он же продублирован типами в начале `src/js/data.js`. Менять формат надо
во всех трёх местах сразу, и `npm run lint` заметит, если типы разойдутся
с кодом.

**Пустой каталог — это ответ, а не поломка.** Если товаров в админке нет,
витрина остаётся пустой. Демонстрационный набор из `data.js` подставляется
только когда блока нет вовсе — то есть в статической сборке, открытой
без WordPress. Раньше эти два случая были склеены, и после удаления товаров
на живой сайт выехали девять демо-диванов с ценами, которых в админке нет.

## Решения и почему так

**Без фреймворка.** Каталог на 41 товар не требует React: его рантайм
весит вдвое больше, чем весь этот сайт целиком. А главное — тогда каталог
пришлось бы рисовать в браузере, и поисковик получал бы пустую страницу.

**GSAP убран.** Анимации появления переписаны на `IntersectionObserver` —
скрипт похудел на 87%. Библиотека тянула 30 КБ ради одного эффекта.

**Никаких стрелок у ленты категорий — своя полоса прокрутки.** На Pointer
Events, видна всегда, тянется мышью. Стрелки на телефоне попадали под палец
и мешали листать.

**Свои шрифты вместо Google Fonts.** Разбиты по наборам символов через
`unicode-range`: браузер качает кириллицу и не качает греческий. Отдельно
пришлось запретить Vite вшивать их в CSS строкой — иначе разбивка теряла
смысл, стили выросли бы с 24 до 46 КБ.

**Постраничный вывод.** По 24 карточки за раз. На медленном телефоне
отрисовка всего каталога занимала 110 мс, с постраничным выводом — 5 мс.

**Всё сверено с Baseline widely available** — по датасету `web-features`.
Ни одной возможности, которая не поддерживается всеми браузерами
последние два с половиной года.

## Тема WordPress

Лежит в `wp-theme/olimp/`. Файлы там **не редактируются руками** — они
собираются из `src/`, правки исчезнут при следующей сборке. Инструкция
для владельца сайта: [wp-theme/olimp/README.md](wp-theme/olimp/README.md).

Внутри темы:

- тип записи «Товар» и таксономия «Категория» — с полями цены, старой цены,
  наличия и метки «Новинка»
- функции `olimp_cards()`, `olimp_tiles()`, `olimp_chips()`, `olimp_count()` —
  печатают каталог в разметку
- `olimp_catalog_json()` — тот же каталог блоком JSON для скрипта
- адреса собранных файлов берутся из манифеста Vite: в именах хеши, чтобы
  браузер не показывал старые стили после обновления

## Проверки

```bash
npm run lint
```

ESLint, проверка типов по JSDoc, Stylelint и linthtml с конфигами HTML Academy.

Проверка типов — это `tsc` по `jsconfig.json`, без TypeScript в коде: он
читает те же комментарии, из которых собирается справочник, и падает, если
описание разошлось с кодом. На первом запуске нашёл три места в рабочем
коде — разобраны в [дневнике](docs/journal.md). Стили держат БЭМ
строго: `selector-max-type: 0`, `selector-max-compound-selectors: 2`.
Исключение сделано только для страницы политики конфиденциальности —
там содержимое приходит из редактора WordPress голыми тегами.

Живой сайт проверялся Playwright в Chromium и WebKit: раскладка на разных
экранах, работа фильтров и корзины, доступность с клавиатуры, скорость
на телефоне с искусственно замедленным процессором.
